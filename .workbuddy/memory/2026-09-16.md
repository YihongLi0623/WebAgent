## 换模型：shopping_admin 评测改用 Qwen3.8-27B-QUASAR-NVFP4

改的是 `Eval/evaluate_shopping_admin.sh`（从 llama.cpp/llama3.1-8b 切到新端点）。

**端点实测结论**（这一步是必要的，直接照 URL 猜会 404）：
- 给定 URL `https://inference.cluster.aimodelnetwork.cn/QUASAR-QAT/Qwen3.8-27B-QUASAR-NVFP4`
  就是**模型名本身构成的路径**，base_url 要写到 `/v1` 为止：
  `.../QUASAR-QAT/Qwen3.8-27B-QUASAR-NVFP4/v1`
  - `.../<model>/models`（少 /v1）→ 404；根路径 `/v1/models` → 404；只有带完整模型路径 + /v1 才 200。
- `MODEL` 必须写**带命名空间的完整 id**：`QUASAR-QAT/Qwen3.8-27B-QUASAR-NVFP4`。
  写短名 → `404 The model 'Qwen3.8-27B-QUASAR-NVFP4' does not exist.`
- 后端 vLLM 0.29.0，`max_model_len=200000`，**不校验 Authorization**（带假 key 也 200）。
- **是思考模型**：思维链被拆到独立的 `reasoning` 字段，`content` 里只剩答案
  （形如 `"\n\n<answer>do(...)</answer>"`）。Eval 只读 `message.content`
  （openai_utils.py:286），所以 reasoning 被拆走不影响动作解析 —— 反而更干净。
  但 thinking 也吃 completion token，故 `MAX_TOKENS` 2048 → **4096**，否则答案易被截断。
- **也是多模态模型**（实测能正确识别 image_url 传入的 1x1 像素颜色）。
  但本评测走文本协议（`observation_type=webrl`），WebRLChatPromptConstructor
  只拼文本 obs、不送图，所以没有启用图像观测，也不需要。
- prompt 模板 `p_webrl_chat_think.json` 的 system prompt 要求输出
  `<think>..</think>` + `<answer>..</answer>`；`extract_action()` 是"有 <answer> 就取标签内"，
  和服务端拆 reasoning 的行为正好对上。`STOP_TOKEN` 改成 Qwen 的 `<|im_end|>`
  （chat 模式本来就把 stop_token 硬编码成 None，仅为一致性）。
- `RESULT_DIR` → `eval_results/shopping_admin_qwen3.8-27b-quasar`；`PARALLEL=4`（用户改的）。

## 修掉"跑完不评分"的 bug

用户上一轮报"运行到第 319 行后报错，没有进行评分"。根因：脚本开头 `set -euo pipefail`，
而 `run_chunk`（即 `python run.py`）**没有任何兜底**。run.py 只要有一个任务抛未捕获异常
就会非零退出 → set -e 让整个脚本在这一行**静默退出**：不打印原因，也跳过后面的计分。
（run.py:582 的 per-task `except` 只包住任务循环内部；`env.close()` 等收尾不在里面。）

三处修改：
1. 定义 `die()` 之后加 `trap '... 第 $LINENO 行失败（退出码 $rc）: $BASH_COMMAND' ERR`，
   任何失败都会打印具体行号 + 命令。（实测 trap 报的行号是失败命令所在行）
2. run 段改成 `run_chunk ... || RUN_OK=0`（并用 `2>&1 | tee logs/run_<时间戳>.log` 留一份全量日志）；
   并行段 `RUN_OK` 承接 wait 状态。
3. 计分改为**无条件执行**：`SCORE_RC=0; score_subset.py ... || SCORE_RC=$?`；
   并在计分前加"体检"：打印 `actions/*.json` 实际条数 / 期望条数，
   不足时自动 tail `error.txt` 和 `logs/chunk_*.log`，再给排查提示。

另外修了两个潜在坑：`n=$(ls ... | wc -l)` 和 `total=$(ls ... | wc -l || echo 0)`。
后者在 glob 无匹配时 `ls` 失败，pipefail 让 wc 已输出的 `0` 和 `echo` 的 `0` 一起进变量，
变成 `"0\n0"`，后面 `[[ -gt ]]` 会语法报错。统一改成 `|| true`（不是 `|| echo 0`）。

已用沙箱验证：假 `python` 让 run.py 故意 exit 3 → 脚本仍走到底并输出计分结果，退出码 0。

## 踩坑：nltk punkt 缺失 → 5 条任务在"计分阶段"丢分

`evaluation_harness/evaluators.py:16` `from nltk.tokenize import word_tokenize`（requirements 钉的是
nltk==3.8.1），而 `StringEvaluator.must_include`（173/174 行）/ `must_exclude`（191/192 行）
真的调用它 → 需要 nltk 的**数据包 `punkt`**，pip 装 nltk 不带数据，所以 conda env 里缺。
报错信息里的 `tokenizers/punkt/PY3/english.pickle` 就是 nltk 3.8.x 的路径（3.9+ 会要 `punkt_tab`）。

**触发面**：35 条里恰好 5 条 —— task_id **108 / 115 / 125 / 126 / 145**，全是
`program_html.required_contents.must_include`（`evaluators.py:429-441`）。
这 35 条的 `string_match` 都没用 must_include/must_exclude，所以只走 program_html 这一路。

**失败模式很隐蔽**：异常发生在 `run.py:542 evaluator(...)`，也就是 agent 跑完 30 步**之后**。
被 `run.py:582` 的 per-task `except` 吞掉 → 写进 `error.txt` → 该任务 `actions/<id>.json`
里 `score` 字段从未写入（写 score 在 548 行，在 evaluator 之后）→ `get_unfinished()`
和 `score_subset.py` 都把它算成**未跑**而不是失败，日志里只有一条 `[Unhandled Error]`。
后果：轨迹白跑，且因 FRESH_RUN=1 下次会重头再跑一遍。

修法：`python -m nltk.downloader punkt`（落到 `~/nltk_data/tokenizers/punkt/`，正好是搜索列表第一项）；
离线就下载 `punkt.zip`（nltk_data 仓库 packages/tokenizers/）解到 `~/nltk_data/tokenizers/`。

**注意评测机（wnds-server，conda env `webagent-r1`，python 3.10）没有外网**：
`python -m nltk.downloader punkt` 报 `urlopen error [Errno 104] Connection reset by peer`，
之后 downloader 自己在交互重试分支上崩了（`AttributeError: 'NoneType' object has no attribute 'id'`，
nltk downloader 的 bug，不是新问题）。已在 Windows 侧下载好
`_nltk_offline/punkt.zip`（13.9MB，含 `punkt/PY3/english.pickle` 正是报错要找的那个）
和 `_nltk_offline/punkt_tab.zip`（4.3MB，nltk>=3.9 才需要），等着 scp 过去解压到
`~/nltk_data/tokenizers/`。

## 控制台"看不到模型回复"与 FAIL 的机制（查清了，别再被绕）

- **模型原文本该打印**：`run.py:502` 有 `print('Action String: ', action_str)`，而
  `--action_set_tag webrl_id` 时 `helper_functions.get_action_description` 直接
  `return action["raw_prediction"]` —— raw_prediction 就是模型那一步的原始输出（agent.py:205/210 赋值）。
  另有一条 `print(f'Agent: {response}')`（agent.py:186）默认关闭：`output_response=False`（agent.py:135），
  run.py:461 没传这个参数。
- **看不到的真因 = stdout 块缓冲**。我加的 `2>&1 | tee logs/run_*.log` 让 stdout 变成管道，
  Python 按 8KB 攒着写；logger 和 tqdm 走 stderr 是逐行刷新的。表现就是"进度条/[Result] 实时，
  Action String 成批延后出现" → 已加 `export PYTHONUNBUFFERED=1`。
- **FAIL = 评测器给分 < 1.0**（run.py:551-554），不是崩溃。每条为什么 FAIL 看产物：
  `actions/<task_id>.json` 的 `actions[]`（= 模型每步原始回复）+ 分数；`screehshots/<task_id>/*.png`
  数量 = 实际步数；`traces/<task_id>.jsonl` 有 html+response（大）。
- **跑得快（~65s）的原因**：每个 step 固定 `sleep_after_execution=3s`，登录/起浏览器 ~10s。
  62-65s ⇒ 只有 4-6 步就结束了，而 max_steps=30 ⇒ 必定是 STOP 提前结束：
  ① 模型自己 `exit(message=...)`（此时评测器 `get_last_action` 取 `trajectory[-1]` 的 message 去比对，
  FAIL 就是答案错，属真实失败）；② 连续 5 个 NONE 动作触发 `run.py:252-261` early stop。
  **`--max_retry` 默认 1 ⇒ 解析失败不重试**，一步格式不对就直接记 NONE。
  解析失败时 actions[] 里的条目是散文（不含 `do(`/`exit(`）；early stop 占位条目的 raw_prediction 是空串 ""。
- 新增工具 `Eval/scripts/inspect_failures.py`：逐条打印 score/步数/截图数/归因
  （PARSE_FAIL_ALL / PARSE_FAIL_PART / MODEL_FINISHED / EARLY_STOP / NO_STEP）+ 最后几条回复。

## [R]/[P] 与"判分器也要调模型"（离线环境必踩）

- `[R]`/`[P]` 只在 `evaluation_harness/helper_functions.py:597-598` 的 `llm_fuzzy_match()` 里打印：
  **R = reference（参考答案）、P = prediction（agent 最后给的答案）**。
  - `[R]` 的来源：`evaluators.py:277` 把 `reference_answers.fuzzy_match` 的列表用 `", "` join 成字符串
    （所以 task 26 打出来是 `01:11, 02:16, ...` 而不是 `['01:11', ...]`）。
  - `[P]` 的来源：`evaluators.py:217` `clean_answer(trajectory[-1]["answer"])`，**会转小写**，
    所以早停时是 `early stop: reach max steps 30`（run.py 里原样是 "Early stop: Reach max steps 30"）。
  - 看到 `[P] early stop: reach max steps 30` = 这条**跑满 30 步且没调 exit()**，即使判分能通也是 0 分。
- **判分模型 ≠ agent 模型**：`agent.py:176` 的 `planner_ip` 只管动作生成；
  `llm_fuzzy_match`(helper_functions.py:600-609) 和 `llm_ua_match`(~645) 是**独立**调
  `generate_from_openai_chat_completion`，**model 写死 `gpt-4-1106-preview`**，
  key/base_url 读 `OPENAI_API_KEY` / `OPENAI_API_URL`。所以离线机器上必然
  `APIConnectionError` → 被 run.py:560 `except openai.OpenAIError` 吞掉 →
  **不写 score（actions/<id>.json 停在 -0.1）→ 算"未跑"**。
- 影响面：35 条里 **8 条**走 GPT 判分 —— task_id **26 / 27 / 30 / 48 / 51 / 59 / 80 / 114**
  （全是 `reference_answers.fuzzy_match`）。其中 4 条值是 `["N/A"]`，但 `evaluators.py:263`
  的判断是 `value == "N/A"`（字符串），拿到 1 元素列表永远为假 → 这 4 条也会走 GPT。
  其余 27 条不需要外部 API，分数有效。
- 三种处理：① `export OPENAI_API_URL/KEY` 指到能出网的网关（脚本 `${VAR:-默认}`，外部优先）；
  ② 把 helper_functions.py:601 / :645 的 model 改成自己网关的完整 id（判分模型就和论文不一致了）；
  ③ 把这 8 条从评测集剔掉，只在同一批任务上做跨模型对比。

## 方法备忘（下次换模型照这个顺序做）

1. `curl <候选 URL>/v1/models` 判断路径形态（带不带 /v1、模型名在不在路径里）→ 拿到准确 model id。
2. `POST /v1/chat/completions` 一次最小请求，看：是否要鉴权、`content` 是否与 `reasoning` 分离、
   `finish_reason`、是否需要更大 max_tokens。
3. 可选：传一张 1x1 png 判断是否多模态（决定要不要提图像观测这条路）。
4. 再改脚本的模型配置区。
